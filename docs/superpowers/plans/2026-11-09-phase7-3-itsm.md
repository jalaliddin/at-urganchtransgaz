# Phase 7.3 (Knowledge base, Problem, Change, Preventive maintenance) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Knowledge base with ticket-form suggestions, problem management with recurring-incident candidates, change
management with approval and conflicts, preventive maintenance plans with generated work items and reminders.

**Architecture:** FormRequest/validation → `app/Services/{Knowledge,Problems,Changes,Maintenance}/*` → models.
Problems, changes and plans carry `organization_id` (`BelongsToOrganization`, `visibleTo`, route binding 404 out of
scope); KB articles are global with audience/status visibility. Status changes re-read the row with `lockForUpdate()`.
Numbers from `NumberSequence`. Frontend `src/features/{knowledge,problems,changes,maintenance}`.

**Tech Stack:** Laravel 13 / PHP 8.3, MySQL 8.4, React 19 + Mantine 9, TanStack Query.

**Spec:** `docs/superpowers/specs/2026-11-09-phase7-3-itsm-design.md`

## Global Constraints

- Every endpoint re-checks organization scope; out-of-scope → 404. Commands/exports apply scope explicitly.
- Status transitions re-read the row with `lockForUpdate()`; reads that guard a write are locking reads.
- Never run backend tests while `make check` runs (shared test DB).
- No raw HTML from article bodies reaches the DOM; no TODO stubs or mock APIs; uz + ru strings for every UI text.

## Review Focus

1. An employee (kb.view only) never sees an `it` article, a draft or an archived article — by list, search, ticket
   suggestions or direct id — Task 2.
2. Two approvers deciding the same change at once, or approve vs cancel at once, leave one decision — Task 4.
3. A change or problem cannot link assets/tickets outside its organization's subtree or the user's scope — Tasks 3–4.
4. `maintenance:daily` run twice creates no duplicate items and sends each reminder once; completing an item creates
   exactly one next item — Task 5.
5. A requester cannot approve their own change, and plan fields cannot be edited after submission — Task 4.

---

### Task 1: Foundations
Permissions + role defaults (spec §3); migration (DATABASE §12); enums (`ArticleType`, `ArticleAudience`,
`ArticleStatus`, `ProblemStatus`, `ProblemPriority`, `ProblemEvent`, `ChangeType`, `ChangeCategory`, `ChangeRisk`,
`ChangeStatus`, `ChangeEvent`, `MaintenanceUnit`, `MaintenanceTaskStatus`, `MaintenanceResult`); asset events
`change_implemented`, `preventive_done`; setting `problems.recurrence_threshold`; models + morph map. Tests: role
permissions, setting default.

### Task 2: Knowledge base
`/kb-articles` (index with search/filters + `filter[suggest]` for the ticket form, show (+views), store, update,
publish, archive, destroy), attachments, `/kb-articles/{id}/vote {helpful}`. Tests: visibility matrix, own vs any,
votes, delete rules, suggestions.

### Task 3: Problems
`/problems` CRUD, `/problems/{id}/transition {status, …}`, `/problems/{id}/tickets` link/unlink, comments,
`/problems/candidates`, `/tickets/{id}/problems`; notifications. Tests: transitions and required fields, scope of links,
candidates, history, notifications.

### Task 4: Changes
`/changes` CRUD (draft only), submit, approve/reject, start, complete (implemented/failed), cancel, revise, affected
assets, conflicts, comments, history, asset events, notifications. Tests: workflow per type, rights incl. self-approval,
conflicts, asset events, concurrent decisions.

### Task 5: Preventive maintenance
`/maintenance-plans` CRUD with assets, `/maintenance-tasks` (filters: status, plan, asset, organization, due range,
mine), complete, skip; `MaintenanceSchedule::next()`; command `maintenance:daily` 07:50; notifications. Tests: schedule
maths, generation once, cancellation, reminders once, complete/skip → next item, asset event.

### Task 6: Dashboard, exports, docs
Dashboard blocks `problems`, `changes`, `maintenance`; exports `problems`, `changes`, `maintenance_tasks`; docs
(DATABASE §12, API §15, OPEN_QUESTIONS Q65+, ROADMAP). Tests.

### Task 7–9: Frontend
7 knowledge base (list, article page with safe Markdown, editor with files, votes; ticket-form suggestions; "create
article" from a ticket). 8 problems (list with candidates, detail with transitions/tickets/history) and changes (list,
form, detail with workflow, conflicts, assets); ticket page problem panel. 9 maintenance (plans with assets and
checklist, work list with complete/skip form), dashboard tiles, navigation, notification types, locales uz/ru,
permission labels. Vitest for the main flows.

### Task 10: Verification
`make check`, browser e2e (desktop + 390px), review, fixes, merge, report.
